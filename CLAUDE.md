# CLAUDE.md

This document describes the deployment architecture and operating conventions for this repository, for use by Claude Code and other contributors.

## Overview

This is a single-repository (monorepo), multi-cloud deployment strategy built on Trunk-Based Development. It manages a static frontend, containerized backend services, infrastructure code, and repository governance from one central location.

## Repository Structure

- `/infrastructure` — Centralized Terraform manifests. The `env` subfolder holds the manifests applied once per environment (staging/prod) using environment-specific variable configurations (`staging.tfvars`, `prod.tfvars`); the `root` subfolder holds shared, manually-bootstrapped resources (see Root Environment below).
- `/services/backend` — Golang backend service(s) packaged as Docker containers targeted for GCP Cloud Run.
- `/services/frontend` — Conventional Vite/React single-page app deployed to Cloudflare Pages.
- Neither service carries its own `lint`/`test`/`build` Makefile: CI runs those through Pants (see Building with Pants below), and local development calls the language's own tooling directly (`go test`, `npm test`, ...) rather than through a wrapper.
- `/.github/actions` — Modular, local GitHub Composite Actions (`action.yml`) encapsulating reusable workflow logic.
- `/.github/settings.yml` — Repository settings, branch permissions, and rulesets managed declaratively as code via the Probot Settings App.
- `/.github/workflows` — Event-specific workflow YAMLs (e.g. pull request, commit, release) that use reusable GitHub Actions.

Each language's manifest lives in the directory that owns that language's code, and the repository root declares no ecosystem of its own: `services/backend/go.mod` is the Go module, `services/frontend/package.json` the npm project, `infrastructure/*/` the Terraform roots. `.github/dependabot.yml` is that same list read back — every `directory` there names the manifest's own folder, and the single entry rooted at `/` is `github-actions`, which genuinely is repository-wide. A manifest at the root would claim the whole tree for one language: a root `go.mod` makes `go mod tidy` walk `infrastructure/` and the frontend, roots editor tooling's workspace at the repository, and would outlive the code that justified it if the Go service were ever removed.

Shared Go code, when there is any, therefore gets a second module beside the first — `packages/go`, consumed through a `require` paired with a relative `replace` — rather than one module hoisted to the root to cover both. Generated code follows its consumer rather than the contract it came from: a shared `.proto` is the shared thing, while the Go and TypeScript bindings generated from it are build output committed for the sake of editor tooling, and belong next to the service that compiles them.

## Commands

What a contributor (or Claude Code) runs locally to check a change before pushing - each language's own tooling, per Repository Structure above, mirroring what `pull-request.yaml` runs in CI:

```
# Backend (services/backend)
go test ./... && go vet ./... && gofmt -l .

# Frontend (services/frontend)
npm test && npm run lint && npm run build

# Protos (packages/protos) - commit the regenerated internal/gen and src/gen alongside the .proto
buf lint && buf format -d --exit-code && buf generate

# Infrastructure
terraform fmt -check -recursive infrastructure

# CI parity (repo root) - only to reproduce a Pants-specific CI failure
pants tailor --check :: && pants --changed-since=origin/main lint check
```

Never run `terraform apply`, `gcloud run deploy`, `wrangler` or anything else that mutates a real environment by hand: every one of those goes through the workflows in CI/CD below. `.claude/settings.json` denies them to Claude Code outright.

In a Claude Code cloud session, `.claude/hooks/session-start.sh` installs the pinned toolchain these need. Two of them still depend on the session's network access: `terraform init`/`validate` needs `registry.terraform.io`, and `pants` currently fails to bootstrap because its bundled Python rejects the session proxy's CA certificate. The Go, npm and buf commands work with the default allowlist.

`.claude/settings.json` also enables the team's Claude Code plugins (`enabledPlugins`, from the marketplaces in `extraKnownMarketplaces`). Locally, Claude Code offers to install them once you trust the folder. A cloud session never installs a repository's plugins itself, so `.claude/hooks/install-plugins.sh` does it, reading the same two keys, in the background at session start. The session has already loaded its plugins by the time the hook runs, so they become active on the next start or resume, or straight away with `/reload-plugins`. To have them from the first message, enable them for your claude.ai account instead, which cloud sessions load as synced plugins.

## Contract Layer

`/packages/protos` holds the `.proto` definitions shared across languages, built with [buf](https://buf.build) rather than plain `protoc`. It exists to close a gap plain Go/TypeScript duplication leaves open: an entity shape declared once in Go (`services/backend/internal/entity`) and hand-copied into TypeScript has nothing enforcing the two agree — a field renamed on one side is caught at runtime, if at all. A shared `.proto` message is instead the one definition both sides generate from.

**Codegen is committed, and CI fails on drift**, deliberately diverging from Pants' default of ephemeral, sandbox-only codegen: ephemeral output means `go mod tidy` errors on generated packages and gopls can't resolve them, needing `pants export-codegen ::` as a workaround for every editor session. Committing costs one CI check (`protos-drift` in `pull-request.yaml`: `buf generate` re-run against the tree, then `git diff --exit-code`) and keeps every editor and Go tool working normally with no extra step. The consequence is the reverse of the usual Pants convention in this repo: `services/backend/internal/gen` and `services/frontend/src/gen` are committed, ordinary first-party source that each language's own Pants dependency inference reads like any other package (`go_package()` for the former, `typescript_sources()` for the latter, both in their own `BUILD` alongside every other package/directory in their tree) — neither is modeled as codegen output at all. Both also carry an explicit `dependencies=["//packages/protos"]` edge onto the `protobuf_sources` target itself (#155), so `pants dependents`/`--changed-since` resolve both generated packages straight from a `.proto`-only edit; before that edge existed, the guarantee came only from `protos-drift` forcing regenerated files into the same commit as their own real import edges, not from the dependency graph itself. That edge is safe only because it's a plain BUILD-graph dependency rather than an import: no protobuf codegen backend is enabled for Go or TypeScript (see `pants.toml`), so neither target's build ever tries to treat `packages/protos` as generation input the way an enabled protobuf codegen backend for that language would.

**Generated code follows its consumer, not the contract it came from** — the same rule the Repository Structure section above states for a future `packages/go`: the `.proto` is the shared thing, while `services/backend/internal/gen` and `services/frontend/src/gen` are build output committed for the sake of gopls/`go build` and tsc/Vite respectively, so each lives inside the service that compiles it rather than in a package of its own. `option go_package` on every proto therefore points directly into `github.com/edgorman/blog.gorman.club/services/backend/internal/gen/...`, resolved by `buf`, not by Pants; the TypeScript side has no proto-level equivalent to `go_package` (`buf.gen.yaml`'s `out:` alone decides where ts-proto writes), but the destination is the same call: `services/frontend/src/gen`, next to the code that imports it, not a shared `packages/node`.

**Every tool version is pinned exactly** — `buf` itself (`bufbuild/buf-setup-action`, SHA-pinned to `v1.47.2` in `pull-request.yaml`, matching the binary used locally), the `protoc-gen-go` plugin (`packages/protos/buf.gen.yaml` invokes `go run google.golang.org/protobuf/cmd/protoc-gen-go@v1.36.12`, the exact version `services/backend/go.mod` requires), and `ts-proto` (a `services/frontend/package.json` devDependency pinned without a `^`, the only npm project in the repo — `packages/protos` has no `package.json` of its own, so `buf.gen.yaml`'s local plugin entry reaches into `services/frontend/node_modules/.bin/protoc-gen-ts_proto` rather than a sibling one). `@bufbuild/protobuf`, the runtime ts-proto's generated `encode`/`decode` import, is likewise pinned exactly as a direct `dependencies` entry rather than left as an incidental transitive dependency of the `ts-proto` devDependency, since it ships in the production bundle. An unpinned version anywhere in this chain would make the drift check fail on PRs that never touched a `.proto`, which is exactly the kind of noise that gets a check disabled rather than fixed.

`ts-proto`'s `opt` flags each earn their keep rather than defaulting: `esModuleInterop=true` matches `tsconfig.app.json`'s `verbatimModuleSyntax`, which rejects ts-proto's default `import * as` star import; `useOptionals=messages` makes only *message-typed* fields optional (`field?: Submessage`), leaving scalars and repeated fields required (`id: string`, `emoji: string[]`) — see the note below on what that does and does not guarantee; `forceLong=string` decodes 64-bit integer fields to `string` rather than pulling in the `long` npm package for a `Long` class this repo has no other use for; `useDate=string` decodes `google.protobuf.Timestamp` to the RFC3339 string the wire actually carries rather than ts-proto's default `Date`, so a generated type matches the response body rather than needing conversion at the fetch boundary; `outputServices=false` is a no-op today (there is no `service` in any `.proto` here, only messages) but states plainly that a gRPC client is not what this layer is for — the backend is reached over plain REST. `strategy: all` on the ts-proto plugin entry is required by ts-proto under buf; it fails in confusing ways under buf's default per-directory invocation.

Pants' own protobuf backends are involved only for linting, never codegen: `pants.backend.codegen.protobuf.lint.buf` runs `buf lint`/`buf format` over `packages/protos` under `pants fmt`/`pants lint`, alongside every other language. That backend registers no BUILD target type of its own, and Pants has no bare, language-agnostic backend that does — the only ones that do (`pants.backend.codegen.protobuf.python`, `pants.backend.experimental.codegen.protobuf.go`) come bundled with that language's actual codegen rules. The Go one is deliberately left disabled, since it is exactly the ephemeral ahead-of-`buf`-generated-output codegen this section opens by ruling out; the Python one is enabled purely as the least-intrusive source of the `protobuf_sources`/`protobuf_source` target types (see `pants.toml`'s comment on `backend_packages`) — nothing in this repo declares a `python_sources` target that would ever trigger its own codegen.

`pants.backend.python` itself has to be enabled too, despite the Repository Structure section above saying this repo has no Python code of its own — protobuf.python's `additional_fields.py` plugs a `python_resolve` field onto every `protobuf_source`/`protobuf_sources` target, and resolving that field is a rule only `pants.backend.python` provides; without it, `pants lint` fails rule-graph construction before it runs anything (`IntrinsicError: ... was not detected in your @rule body at rule compile time`), not just at the unused field. With no `python_sources` target anywhere in the repo, this backend's own goals have nothing to act on, so it costs nothing beyond the one line in `backend_packages`.

`[python-protobuf] infer_runtime_dependency = false` sits beside it for the same reason: protobuf.python's default assumes whatever consumes its generated Python needs the `protobuf` PyPI package at runtime, and checks for a `python_requirement` providing it at `pants lint` time - not only when codegen actually runs. Since nothing here ever generates or consumes Python bindings from `packages/protos`, there is no such requirement to add, so the check is turned off rather than satisfied with an unused one.

Pants' TypeScript backend has no protobuf codegen counterpart at all (unlike the Go and Python ones discussed above, there is no `pants.backend.experimental.codegen.protobuf.typescript` to even consider enabling or disabling), so nothing about ts-proto's generation is Pants-driven in the first place - the same `buf generate`/drift-check pipeline that already governed the Go side is simply pointed at a second output directory.

`blog.v1.AllowedEmojis` was the first message here and remains the smallest: it mirrors `entity.AllowedEmojis` and is used only as a *type* (`AllowedEmojis['emoji']` in `ReactionBar.tsx`), sharing a shape rather than values — both sides still write the five emoji out as literals. It proved the generate-and-verify pipeline; it is not what the layer is for. #168 is migrating every message that actually crosses the wire; #171 (below) is the sub-issue that revisited whether the values themselves should move in here too, and kept them out.

**Protos model the wire, not the domain and not the datastore.** Three representations already exist and this adds none: `internal/entity` carries validation and policy (`SetTitle`, `Permission`, `Subscribed`) and stays hand-written; `internal/repository/firestore` has its own `...Document` structs with converters; `internal/service` is the wire, and that is what `packages/protos` defines. The distinction is not theoretical — `blogv1.User` has no `subscribedUntil` at all because a public lookup must never disclose one, while `blogv1.CurrentUser` does, since an account may see its own. One entity, two wire messages. Generated structs cannot replace entities in any case: they carry `protoimpl` state Firestore would try to persist, and none of the entity methods.

**Responses are marshalled with `protojson`, not `encoding/json`** (`internal/service/respond.go`), because `encoding/json` on a generated struct walks its Go fields — protoimpl state included — and ignores the `protobuf` tags that decide names, presence and well-known-type encoding. Four settings there are the whole compatibility story between the two, and were chosen against captured response bodies rather than by reasoning:

- **`EmitDefaultValues`**, not `EmitUnpopulated`. Bare `protojson` drops zero-valued scalars, which would turn `"assistantEnabled": false` into an absent field and a client's `undefined`. `EmitUnpopulated` overcorrects the other way and emits `null` for unset *message* fields, which would start sending `"subscribedUntil": null` where the field is absent today. `EmitDefaultValues` is the one that matches `encoding/json`'s behaviour.
- **`UseProtoNames` off** (the default), so the wire stays lowerCamelCase — `createdAt`, not `created_at` — matching the hand-written `json` tags it replaced.
- **`DiscardUnknown` on for requests.** `protojson` rejects an unrecognized field by default where `encoding/json` ignores one; without this an older or newer client sending a field this version does not know would get a `400` where it used to be accepted. It is also what makes an additive proto change safe to deploy ahead of the client that sends it.
- **Output is compacted before it is written.** `protojson` deliberately varies its whitespace between builds, so the same message marshals to `{"id":"x","bio":""}` in one binary and `{"id":"x", "bio":""}` in the next. Two identical requests answering with byte-different bodies is a poor property for an HTTP API — it would quietly defeat any response caching or ETag added later — so `writeProto` normalizes it.

**Timestamps are `google.protobuf.Timestamp` with ts-proto's `useDate=string`**, so Go keeps `timestamppb` and TypeScript sees the RFC3339 string the wire actually carries rather than a `Date` the response body never held. The cost is that a message field has presence, so the generated type is `createdAt?: string` where a hand-written interface said `createdAt: string`. That is the wire telling the truth rather than a regression — `protojson` may omit a message field — and call sites guard it.

**`useOptionals=messages` leaves scalars required**, which is what proto3 semantics and `EmitDefaultValues` together guarantee: a scalar is always on the wire, a message may be absent. Both this file and `buf.gen.yaml` previously described the flag as making *every* field optional — it does not, and #169 corrected both. The practical consequence is the `createdAt?: string` above: optionality tracks whether a field is message-typed, not whether the server always sets it.

**`Visibility` is a plain `string` field, not a proto `enum` (#170).** `blogv1.Blog.visibility` and `blogv1.BlogRequest.visibility` carry the same `"public"`/`"private"` values `entity.Visibility` always has, unconverted. A proto3 `enum` was the other option on the table: it would give the field a closed set of valid values at the type level, on both sides, in place of a plain string either side could still send garbage into. Three things ruled it out together, not any one alone. First, wire compatibility: `protojson` serializes an enum by its member *name*, so the wire value would become `VISIBILITY_PUBLIC`/`VISIBILITY_PRIVATE` — a breaking rename of a value every stored client expectation and frontend comparison (`post.visibility === 'private'`) already depends on, for a field with no bug to fix. Second, proto3 requires an enum's first value to be its zero value, conventionally an `_UNSPECIFIED` member — but a `Visibility` has no unspecified state to model: `entity.Visibility.Valid()` accepts exactly `"public"` or `"private"` and nothing else, so an enum would need a third member that does not correspond to any value `SetVisibility` ever actually accepts, splitting the two representations of validity rather than unifying them. Third, the type safety an enum buys server-side already exists: `entity.Visibility` is a distinct Go type with its own `Valid()`, and every wire value passes through `SetVisibility` before it is ever stored (see `applyBlogRequest` and `Access Control` below) — an enum on the wire would duplicate a check that already runs, at the cost of a breaking rename. The frontend gets its own version of the same guarantee by construction rather than from the generated type: `api.ts` declares `export type Visibility = 'public' | 'private'` by hand, since the wire field itself is typed as a plain `string` and carries no such constraint of its own; `EditPost.tsx` casts the one value that arrives already validated by the server (`post.visibility as Visibility`) rather than re-deriving the union from `Blog['visibility']`, since that derivation would silently widen to `string` the moment the wire type does. Weaker at the type level is the accepted cost, and it is deliberately not the same cost `entity.Visibility.Valid()` and `SetVisibility` still pay in full on every write.

**`Comment`, `ReactionCount`, `TargetReactions`, and `PageReactions` (#171)** are the reader-engagement half of #168, and the two proto files behind them read as opposites of each other. `comment.proto`'s `Comment` follows `Blog`'s and `User`'s shape exactly: `author_username` is resolved server-side and has no counterpart on `entity.Comment`, the same reason `Blog.author_username` and `User`'s absent `subscribedUntil` are shaped the way they are (see "Protos model the wire" above); `entity.Comment`'s own moderation rules (who may delete it) stay hand-written policy. `reaction.proto` is the opposite case, and the more interesting one: `ReactionCount` and `PageReactions` have no entity to mirror at all, because what crosses the wire is an aggregate folded fresh from every reader's stored `entity.Reaction` rows (`countReactions`), not a stored row itself - the wire shape and the datastore shape were never the same thing to begin with, so there was no entity migration to even consider. `TargetReactions` (a `repeated ReactionCount` wrapper) exists purely as plumbing this pair needs and the issue didn't name: protojson can only marshal a message, never a bare top-level array, and a map value must be a message too, so both `PutReaction`/`DeleteReaction`'s response and each entry of `PageReactions.comments` need a one-field wrapper around the list `reactionCount[]` used to be. `PutReaction`/`DeleteReaction` read no request message at all - reactions are addressed (`PUT`/`DELETE .../reactions/{emoji}`) rather than toggled, so the target and the emoji are already both in the URL and the reader is the credential, leaving no body to decode.

**The `AllowedEmojis` values question (#171) is answered: leave them as literals, on both sides, permanently rather than provisionally.** The issue that added `blog.v1.AllowedEmojis` (#168's sub-issue) left this open - move the five glyphs themselves into the proto so both sides read one source, or keep sharing only the shape. Moving them in was ruled out, for two independent reasons rather than one. First, mechanically: proto3 has no field-level or file-level default for a scalar list that both `protoc-gen-go` and ts-proto would read back as the same constant without a custom protobuf option plus runtime reflection on both sides to retrieve it - a mechanism to build and maintain, not the small change the issue was sized as. Second, and more basically: the five glyphs are policy - exactly what `entity.ValidEmoji` decides, and this layer models the wire, not policy, which is the same line that keeps `entity.ValidEmoji` itself hand-written per #110's carve-out ("Protos model the wire" above). Putting the values in the proto would mean policy data living in the one place this repo has deliberately kept wire shape only. So `entity/emoji.go` and `ReactionBar.tsx` each keep their own literal `[]string`/`string[]`, typed against `AllowedEmojis['emoji']` / `genblogv1.AllowedEmojis.Emoji` rather than generated from it - a rename or resize of the field still breaks both builds, but the two lists' *values* can still drift, which is the accepted and now-documented trade rather than a gap to close later.

**A wire change is a two-release problem, deliberately accepted.** Production Releases deploys the backend at step 2 and the frontend at step 3, so between them a new backend serves the previous bundle. For this repository that window is short and the blast radius is one blog, so changes are not required to be additive across two releases — but the ordering is why `DiscardUnknown` is on, and why anything larger than a field rename should be checked against it before shipping.

Giving Go a second module of its own (`packages/go`, once a second Go consumer of shared code exists — see Repository Structure above) is still deliberately left for follow-up work.

## Cloud Infrastructure & Security Isolation

### Isolated GCP Projects

To maintain strict blast radius boundaries, environments live in distinct GCP projects:

- `blog-gorman-club-stag` — Hosts staging services and serves as the isolated sandbox for testing. Future feature: ephemeral/PR environments.
- `blog-gorman-club-prod` — Hosts live production infrastructure and sensitive datastores.

### Root Environment

A third, non-application Terraform root lives at `/infrastructure/root` and provisions the `blog-gorman-club-root` GCP project itself, along with the resources shared across staging and prod: the `blog-gorman-club-stag` and `blog-gorman-club-prod` GCP projects, the Terraform state buckets for all environments (root included), the GitHub Actions WIF pool/provider, and any domain configuration shared between the two environments (e.g. the parent DNS zone). It also enables the baseline set of GCP APIs uniformly across root and both environment projects, so the per-environment Terraform roots can assume those APIs are already on.

Only root's very first apply is manual — it has to exist before any pipeline has credentials or state to work with, so it can't be bootstrapped by the CI/CD it enables. Because the root project's own state bucket doesn't exist until root has been applied once, that first `terraform apply` runs against local state; once the GCS bucket it creates exists, state is migrated into it (`terraform init -migrate-state`) and the local state files are discarded.

Every apply after that one-time bootstrap goes through the ordinary CI/CD flow, same as `blog-gorman-club-stag` and `blog-gorman-club-prod`: a `pull-request` workflow plans against `/infrastructure/root` for PRs that touch it, and a `push-commit` workflow applies it on merge to `main`, both authenticating with the WIF identity that bootstrap itself created.

### IAM & Authentication

Workflows authenticate to GCP using Workload Identity Federation (WIF) over short-lived OIDC tokens, avoiding long-lived JSON keys. A single GitHub Actions service account is created in the root environment and granted IAM roles on each project (root, staging, prod) individually — never a broad org-level grant — and the WIF provider's attribute condition restricts it to OIDC tokens asserting this specific GitHub repository. The resulting Workload Identity Provider path and service account email are written into GitHub Actions repository variables by the root apply, so workflows never hardcode them.

The one credential WIF can't replace is the GitHub PAT root's own Terraform needs to write those repository variables in the first place. It's supplied by hand only once, at bootstrap; every apply after that (including CI's) reads it back from a `github_provider_token` secret in GCP Secret Manager, fetched at the start of each workflow run using the WIF identity above — so it's never stored as a GitHub Actions secret.

### AI Writing Assistant

The backend calls Gemini models on the **Gemini Enterprise Agent Platform** — the product formerly called Vertex AI, whose API is still served at `aiplatform.googleapis.com` (its discovery document is now titled "Agent Platform API"). It authenticates as the Cloud Run runtime service account (`roles/aiplatform.user`) over Application Default Credentials rather than with an API key, which is the same reasoning that put CI on Workload Identity Federation: there is no long-lived credential to store in Secret Manager, rotate, or leak.

The platform is chosen over the **Gemini API** (`generativelanguage.googleapis.com`) for exactly that reason. The Gemini API's `generateContent` declares no OAuth scope in its discovery document, so it accepts an API key and nothing else; a token-authorized request to it is refused with a `403`. Only this platform's `generateContent` declares the `cloud-platform` scope, and so accepts the credential the deployment already has. Reaching for the Gemini API instead would mean introducing the one long-lived secret this architecture is built to avoid.

The model id and its location are Terraform variables (`assistant_model`, `assistant_location`) rather than constants, since model availability is regional and model ids change faster than this service is redeployed.

Access is an entitlement, and it is expressed in the same access model as every other rule (see Access Control below): a whitelist whose membership is worked out per request rather than stored on a document. An account is entitled while its subscription has not expired (`subscribedUntil` on its profile) and no other way - there is no per-environment allowlist to be on, so granting access is writing that field and revoking it is clearing it, neither of which needs a deploy. It is set by hand until a checkout writes it. The subscription is keyed on the account rather than on an address: the profile is loaded by the uid in the verified ID token, so nothing a request asserts about itself is consulted, and a username - freely chosen and, once released, claimable by anybody - is never what access follows.

The entitlement says who may spend, not how much, so volume is bounded separately: assistant turns are rate limited per account by the backend, on a much tighter budget than any other route, because a turn is the only request that calls a paid model. The buckets are held in the serving process, which makes them per-instance budgets and is the one thing to revisit if the service ever scales past a single instance (see `services/backend/README.md`).

### Access Control

Who may do what is one model rather than a rule per feature (`services/backend/internal/entity/access.go`). Every **resource** - a post, a profile, a comment, a reaction, and the assistant as a gated feature - declares an **access** mode for each **action** on it (`read`, `create`, `update`, `delete`), and there are exactly three modes: public (everybody, signed in or not), private (the owner alone), and whitelist (the owner plus whoever was named beside them). A single policy table holds every pair; one it does not declare is refused, so a feature added without a line in it is closed rather than open.

A post is the one resource that chooses its own read audience: its `visibility` and `allowedUserIds` *are* the three modes, read back as one. The assistant is the one whitelist that is not a field on a document - its membership is the subscription above. There are deliberately no roles: every rule here is decided by who owns a thing, who was named on it, or what an account has paid for, all of which a role would sit between rather than answer. See `services/backend/README.md` for how a permission is asked and why a refused read is a `404` rather than a `403`.

### Reader Engagement

Posts carry comments and reactions, both stored in Firestore beneath the post
they belong to and both governed by the post's own read rules rather than rules
of their own. Reactions are a fixed set of five emoji (`entity.AllowedEmojis`),
not custom or combined ones, and they are addressed (`PUT`/`DELETE`) rather
than toggled so a retried click is harmless. See `services/backend/README.md`
for the ownership and moderation rules.

### Finding Posts

The feed is reverse-chronological, so `GET /blogs` carries two filters beside
the `ownerId` a profile feed uses: `tag` narrows to one topic and `q` to a
case-insensitive substring of a post's title or body. Both narrow the same feed
and neither can widen it - each is applied on top of the read rules above, so a
search can never surface a post the caller could not already have scrolled to,
and a tag says nothing about who may read a post.

Tags are normalized on the way in (lowercase, one hyphen between words), so the
form a post is stored, filtered, and linked under is decided by the server
rather than by however an author typed it. A tag becomes a Firestore
`array-contains` filter with its own composite indexes, and replaces rather than
joins the readability OR the general feed uses - a query may hold only one
`array-contains` clause, and a tag is the more selective of the two, so
readability falls back to the same in-Go filtering a profile feed already
relies on.

Search is deliberately a substring scan applied as the feed is walked, not a
search index: there is no Firestore predicate for it, and at this scale the
alternative is a service to run, pay for, and keep in step. It is bounded and
paged, and is the first thing to revisit if the collection outgrows it.

### Caching

`GET /blogs` is the highest-traffic and most repeated read in the service - the
landing feed is the same public data for every signed-out visitor - so the
anonymous listing is cached in the serving process for a short TTL
(`services/backend/internal/repository/cache`). It is a decorator over the blog
repository rather than something a handler does, wired in `cmd/backend`: the
service cannot tell a cached page from a fetched one, and the cache is removed by
deleting a line.

Only the anonymous caller's pages are cached, and that is what makes it safe
rather than something to be careful with. A page is whatever the read rules above
admit for one uid, so two callers may share an answer only if they share a uid -
and the empty uid, which is not an account at all, is granted public posts and
nothing else. A signed-in caller's page carries their own private and whitelisted
posts, so it is neither stored nor served here; there is no per-uid keying to get
wrong because there are no per-uid entries. Every filter is part of the key, so a
tag or a search is its own entry rather than a variation on the feed.

A write drops every cached page, so an author sees their own post in the feed at
once; across instances the TTL is the real bound, since the cache - like the rate
limiter's buckets - is held per-instance and is the same thing to revisit if the
service scales past one. Entries are capped, because a caller sending a distinct
search term per request would otherwise grow the map indefinitely; the read volume
such a caller can provoke is bounded by the rate limiter rather than by the cache.

### Resource Naming

Strict environment suffixes (`backend-stag`, `backend-prod`) and scoped secrets (`stag-db-pass` vs `prod-db-pass`) ensure services in staging cannot accidentally reach production resources.

### Artifact Stores

Every service has one store per environment project rather than one shared store copied between them: the backend publishes to that project's own Artifact Registry `backend` repository, and the frontend to that project's own `<gcp-project-id>-frontend` Cloud Storage bucket (`infrastructure/env/storage.tf`) - named after the project rather than just the environment because bucket names are global across GCS, unlike the project-scoped resources named elsewhere in this document. The GitHub Actions service account is granted write on both stores in staging and prod alike (per-project, per the IAM section above, never a broad grant), so either can be published straight into every environment's store from the job that builds and validates it.

Both services are there now: Staging Deployments (below) publishes the SHA-tagged backend image and the SHA-folder frontend build to both stores on every merge, and Production Releases deploys straight from `blog-gorman-club-prod`'s own store for each service rather than copying into it. Neither promotion reads across the project boundary or copies anything - each project's store is written once, by the job that built and validated it, and only read from within that same project.

Every merge writes to both projects' stores regardless of whether that merge is ever promoted (see Staging Deployments below), so a store's size tracks merge volume, not deploy volume - prod's own registry and bucket fill up from commits even across a long gap between promotions. Nothing deleted any of it until now, so both stores grow forever. `infrastructure/env/artifact_registry.tf` and `storage.tf` each carry one cleanup rule, applied identically in both projects since neither store's retention need differs by environment:

- The backend repository's `cleanup_policies` keep the `backend_registry_keep_count` (default **30**) most recently uploaded versions and delete everything else - Artifact Registry's documented pattern for "keep only the N most recent," a KEEP policy pinning the most recent N versions combined with an unconditional DELETE policy for the rest. Thirty is sized off versions rather than days on purpose: a rollback goes back by release, not by calendar time, and thirty covers even this repository's busiest stretch of development (a dozen-odd merges in a single day) several times over, while a normal cadence of a few merges a week reaches back months. There is no cleanup policy condition for "a version a Cloud Run revision still references" - Artifact Registry cannot express that - so the guarantee is indirect: as long as prod is promoted well within every 30 merges to `main`, the image any Cloud Run revision is running always falls inside the kept window. If a gap ever approaches that, promote (or raise `backend_registry_keep_count`) before it closes.
- Each frontend bucket's `lifecycle_rule` deletes commit-SHA folders older than `frontend_retention_days` (default **90**) days. GCS lifecycle conditions are age-based only - there is no "keep the N most recent objects" equivalent for distinct object names the way Artifact Registry has one for versions - so this cannot single out "the folder currently deployed to prod" independent of how long ago it was promoted the way the registry's keep-count can single out recent versions by count. Ninety days is chosen generously against that: it comfortably outlasts any promotion gap seen in this repository so far, but the same operational rule applies - promote (or raise `frontend_retention_days`) before a live folder's age approaches the window, since nothing here can tell a live folder from an old one by age alone.

Both are dry-run before they can delete anything for real: the registry ships with `cleanup_policy_dry_run = true` (Artifact Registry's own dry-run mode - it evaluates and logs what the policy would delete without deleting it), and the bucket rule has no such built-in mode, so it needs a one-off listing of what it would currently match (`gcloud storage ls -L` filtered on creation time against `frontend_retention_days`) reviewed before it is relied upon. Enabling real deletion (flipping `cleanup_policy_dry_run` to `false`) is a deliberate follow-up once the dry-run output has been reviewed against what is actually serving each environment, not part of adding the policy itself.

## CI/CD, Branching, & Release Lifecycle

All build, test, infrastructure provisioning, and deployment pipelines run exclusively through GitHub Actions (bypassing GCP Cloud Build). Sequential execution rules ensure infrastructure provisioning completes successfully before service updates occur.

### Building with Pants

[Pants](https://www.pantsbuild.org/) is the CI build/lint/test orchestrator for the whole repo, cut over from the parallel Makefile/`paths-filter` pipeline it was proven green alongside for #110-#119 (see #120). `pants.toml` sits at the repository root because Pants is the build orchestrator itself, not a language manifest - it claims no directory and generates no code of its own, only pointing at the manifests that already exist (`services/backend/go.mod`, `services/frontend/package.json`, `infrastructure/*/*.tf`), so it isn't the root ecosystem file the Repository Structure section above rules out. `pants.ci.toml` layers CI-only settings on top via `PANTS_CONFIG_FILES`, applied by the `pantsbuild/actions/init-pants` composite action: a quieter, non-interactive UI, and (since #120) read+write remote caching over the GitHub Actions cache - `[GLOBAL] remote_cache_read`/`remote_cache_write` are ordinary Pants options, not a backend, and have nowhere to point without `init-pants`'s own `experimental-remote-cache-via-gha: 'true'` input (set on every call that uses this config, in both `pants-setup` and `pants-changed`), which exports `PANTS_REMOTE_STORE_ADDRESS`/`PANTS_REMOTE_OAUTH_BEARER_TOKEN` from the runner's own GHA cache credentials. `remote_provider` also has to move off its default `reapi` (a gRPC remote-execution service, so it only accepts `grpc://`/`grpcs://` addresses) to `experimental-github-actions-cache`, since the address init-pants exports is a plain `https://` URL to GitHub's own cache service. The GHA cache wasn't reachable when #110 first tried it (every read/write errored with a 400 "Our services aren't available right now"); enabled now, it's what makes a second CI run against an unchanged tree fast rather than merely correctly empty.

`get-pants.sh` sits at the repository root too, for the same "not a language manifest" reason `pants.toml` does - it's [Pants' own installer](https://www.pantsbuild.org/stable/docs/getting-started/installing-pants) for the `pants` launcher binary (scie-pants), vendored verbatim rather than curled fresh each time: Pants' own docs advise against "curling this script directly to bash... on every CI run" and recommend checking it into the repo instead, since a compromise of the hosted script during some window would otherwise be re-fetched on every run rather than caught once at review time. `init-pants` (above) already looks for `./get-pants.sh` at the repo root before falling back to downloading one itself from a pinned `setup-commit`, so committing it here needed no workflow change - it's picked up automatically. The file is vendored from the exact commit `init-pants`'s own default `setup-commit` already pins, so this changes what gets *fetched from*, not what's *trusted*. It also lets the Claude Code cloud session's `SessionStart` hook (`.claude/hooks/session-start.sh`) install the same `pants` launcher without reaching `static.pantsbuild.org`, which isn't in a cloud session's default network allowlist.

CI no longer decides what to lint, check, or test with a hand-maintained glob (`dorny/paths-filter`) or a per-service job (the old `services-{frontend,backend}` jobs and their `Makefile`-driven `backend-test`/`frontend-test` composite actions, and the `services-{frontend,backend}-pants`/`infrastructure-pants` jobs that ran alongside them advisory-only): both service Makefiles and all four of those composite actions/jobs are gone. `pull-request.yaml` instead runs Pants' own [CI-recommended pair](https://www.pantsbuild.org/dev/docs/using-pants/using-pants-in-ci) against the diff, via the generic `.github/actions/pants-setup` (Go + Node + `init-pants`, since a repo-wide invocation can touch any backend):

```
pants --changed-since=origin/main lint check
pants --changed-since=origin/main --changed-dependents=transitive test package
```

Linting doesn't need dependents - a change to a leaf file doesn't require re-linting its callers - but a test does: changing a shared package must re-run every test that exercises it, which is what `--changed-dependents=transitive` supplies. This is also why a docs-only PR runs no tests and a backend-only PR runs backend tests and not frontend ones: Pants computes the affected target set itself from the diff, rather than a filter naming `services/backend/**`/`services/frontend/**` by hand. `package` rides the same invocation as `test` (#156), since `services/backend:image` (the `docker_image` target discussed below) needs the identical affected-target set - a break in it, or in its hand-declared dependency list, now surfaces on the PR that causes it instead of first on merge to `main`, inside the job that publishes the artifact. **The frontend bundle is not built through Pants at all**, despite what #119 intended. `lint-check` runs `npm run build` directly, next to `go vet` and oxlint, for the same reason those are there: the goal is that a broken bundle fails the PR rather than the merge job that publishes it, and Pants is not the shortest path to that here.

The history is worth recording, because the BUILD file looked correct for a long time while doing nothing. `node_build_script` is a **field value, not a target** - which is why it rejects `name=`, the symptom #119 hit and worked around by dropping the argument - so it belongs in `package_json`'s `scripts=` list. From #119 onward `services/frontend/BUILD` called it as a bare top-level statement, which constructs the object and discards it. The vite build was therefore never in the target graph: `pants package services/frontend::` exited in 190ms having matched nothing, which made both #146's "green in CI" and #156's first attempt at a packaging step vacuous passes rather than working builds.

Registering it properly (`package_json(scripts=[node_build_script(...)])`) makes the build real and immediately fails, because the sandbox a build script runs in is the `package_json` target's declared dependencies plus the npm install, not the directory tree - and nothing `import`s a tsconfig, `index.html` or a `public/` asset, so dependency inference reaches none of them: `error TS6053: File '.../services/frontend/tsconfig.json' not found`. Behind that sit `tsconfig.app.json`, `tsconfig.node.json`, `index.html`, every `public/` asset and most likely every `src/` target, all of which would have to be hand-declared - re-creating, in one `dependencies=` list, the per-file enumeration #155 removed from eight BUILD files. That trade isn't worth it for two services, so the `node_build_script` is left off deliberately and `npm run build` runs directly. Revisit if Pants' JavaScript backend grows inference for a project's own build inputs.

The backend image is the opposite call and worth contrasting: its hand-declared dependency list is three entries and buys a `docker build` that CI already depended on, so `pants package` owns it.

`pants.backend.experimental.go.lint.vet` stays disabled: its `go vet` invocation never changes into the module's own directory, so it only works when `go.mod` sits at the Pants build root - upstream, unfixed as of `pantsbuild/pants@main`. Since `services/backend/go.mod` deliberately doesn't (#114), `vet` fails every package; `gofmt` (lint) and `check`/`test` (which don't need module discovery) are unaffected. Re-enable it once that's fixed upstream.

`services/frontend/src` collapsed from eight one-target-per-directory BUILD files down to two (#155): `src/BUILD` itself, using `**/*` globs so a `tsx_sources`/`typescript_sources`/`_tests` target picks up every matching file anywhere under `src/` without naming it, and `src/gen/BUILD`, kept apart since it also carries the `packages/protos` dependency discussed above. That second file was `src/gen/blog/v1/BUILD` until #169: ts-proto writes a directory per proto package, so importing `google.protobuf.Timestamp` produced `src/gen/google/protobuf/` — a directory no BUILD file owned, and a `tailor --check` failure. One recursive target at `src/gen/` covers whatever a future proto imports instead. The per-directory split had bought very little `--changed-dependents` precision at this size: `tsx_sources`/`typescript_sources` are target generators regardless of how the glob is written, so each matched file was already its own atomic target under either layout - collapsing the BUILD files changes nothing about test-selection granularity, only how many files enumerate it by hand. Two files stay out of the glob rather than joining it: `setupTests.ts` (Jest's `setupFilesAfterEach` entry) and `vite-env.d.ts` (Vite's ambient type declaration) are never `import`ed, so dependency inference can't reach them, and every test target needs one explicit dependency to pick them up. Keeping that pair in their own narrow `typescript_sources(name="ts")` target, rather than folding them into the tree-wide one, keeps that blanket dependency small; folding them in would make every test target an implicit dependent of every unrelated `.ts` file in the tree, which is exactly the imprecision `--changed-dependents=transitive` exists to avoid. `pants tailor --check ::` now runs in `lint-check` (`pull-request.yaml`), so a source file added anywhere without a covering target - the same silent-gap failure mode the per-file enumeration it replaced was already exposed to - is a CI failure rather than a test that quietly never runs; it runs over the whole repo (`::`) rather than `--changed-since`, since a missing target is a property of the tree, not of the diff. The one file that needed a target purely to satisfy it, `services/frontend/public/theme.js` (a classic script tag in `index.html`, so nothing imports it), is owned from `services/frontend/BUILD` reaching down into `public/` rather than from a `public/BUILD` of its own: Vite copies that directory into `dist/` verbatim, so a BUILD file placed inside it is published to both frontend buckets and served at the site root, which is what happened between #159 and the fix.

The backend's container image is modeled as a `docker_image` target (`services/backend:image`) over the existing multi-stage Dockerfile unchanged, not - as #117 first tried - a `go_binary` dependency with the Dockerfile reduced to its runtime stage. That would have meant the packaged binary only exists inside a Pants-assembled build context, breaking the plain `docker build services/backend` that `backend-deploy/action.yml` still runs on every merge; #117 leaves that path alone. The `COPY . .` this keeps means Pants' Dockerfile dependency inference - which only resolves literal `COPY` sources, not `.` - can't find the target's dependencies on its own, so they're declared by hand as `services/backend/cmd/backend`, whose ordinary Go import inference already reaches every `internal/` package it imports; that's the edge `pants dependents` needs to reach the image from an `internal/` change. `extra_build_args=["COMMIT_SHA"]` mirrors the `--build-arg COMMIT_SHA` the deploy action already passes, reading it from whatever CI sets before invoking `pants package` and falling back to the Dockerfile's own `ARG COMMIT_SHA=unknown` locally. `[docker.registries]` in `pants.toml` registers the real `stag`/`prod` Artifact Registry paths so a target can reference them by `@stag`/`@prod`, but both are `skip_push` and neither `default` - nothing publishes a Pants-built image yet. `pull-request.yaml`'s `test` job does now run `pants ... test package` (#156), so this target is built - not published - on every PR that reaches it, closing the gap #120 opened when it retired the advisory `pants package services/backend::` step along with the job that ran it.

Terraform is modeled the same hand-written way, since [Pants' Terraform backend](https://www.pantsbuild.org/dev/docs/terraform) has no tailor support: `infrastructure/env` and `infrastructure/root` each get a `terraform_module`, and each of `infrastructure/config/{staging,prod,root}` gets a `terraform_deployment` pointing at the matching root module. Pants auto-associates a `terraform_backend` and `terraform_var_files` target with a `terraform_deployment` in the same directory, which is exactly how `infrastructure/config/<env>/` was already laid out (`terraform.tfbackend`, `terraform.tfvars`). That graph is now load-bearing rather than advisory: `.github/actions/pants-changed` runs `pants list --changed-since=<ref> --changed-dependents=transitive` and checks whether each of `infrastructure/config/{root,staging,prod}:deployment` shows up, which is what decides whether that environment's real `terraform plan` (PRs, via `pull-request.yaml`'s `infrastructure-{root,staging,prod}` jobs) or `terraform apply` (merges to `main`, via `push-commit.yaml`) runs - `infrastructure/env:mod` is a dependency of both `infrastructure/config/staging:deployment` and `infrastructure/config/prod:deployment`, so a change to `infrastructure/env/**` resolves to both without either being named in a glob, closing the gap the old `github-file-diff` paths-filter used to paper over by listing `infrastructure/env/**` in both the staging and prod filters by hand. The one thing that graph can't see is a composite action - Pants has no target type for `.github/actions/terraform-pull-request` or `.github/actions/gcp-secret-manager` - so `github-file-diff` still carries one glob, scoped down to `.github/**` alone, ORed on top of the Pants-derived result in both workflows' `changed` job. `[download-terraform]` in `pants.toml` pins the same `1.15.8` the `terraform-pull-request`/`terraform-push-commit` actions install via `hashicorp/setup-terraform`, since `required_version` in `infrastructure/*/providers.tf` is an exact pin and Pants' default known Terraform versions don't reach that high. Enabling the backend also requires `[python] interpreter_constraints` in `pants.toml`, even though this repo has no Python code of its own: the backend's dependency inference parses `.tf` files with a Python-implemented HCL2 parser that Pants runs as a PEX, which needs an interpreter regardless. `[download-terraform] extra_env_vars = ["PATH"]` pulls the host's `PATH` into the sandbox terraform processes run in: `pants.backend.terraform.tool.setup_terraform_process` builds that sandbox's `PATH` solely from a `"PATH"` entry in this list, so with none listed it was `""`, and `terraform init`'s provider installer failed every download with `exec: "getent": executable file not found in $PATH` (needed for DNS resolution) before ever reaching the network.

### Commit Message Convention

Every PR title must be a valid [Conventional Commit](https://www.conventionalcommits.org/en/v1.0.0/) subject — `type(scope)?: description`, e.g. `feat(backend): paginate GET /blogs` — because the repo squash-merges every PR (`.github/settings.yml` sets `squash_merge_commit_title: PR_TITLE`), so the PR title becomes the subject line of the one commit that lands on `main`, and that's what Versioning (below) actually parses. Use `feat:` for a new capability, `fix:` for a bug fix, and any other Conventional Commits type (`build`, `chore`, `ci`, `docs`, `perf`, `refactor`, `revert`, `style`, `test`) for a change that shouldn't move the version on its own. Mark a breaking change with `!` after the type/scope (`feat!:`) or a `BREAKING CHANGE:` footer in the PR body — either bumps major regardless of type. A title that doesn't match any recognized type still merges fine; it just falls back to a patch bump, same as everything did before this convention existed. This applies to Claude Code equally: title PRs it opens the same way.

### Versioning

Releases use plain semantic versioning — `major.minor.patch`, with no `-rc.N` or other pre-release suffix on the tag itself (pre-release vs. formal release is tracked via GitHub's release "prerelease" flag, not the tag name). The bump on every merge to `main` is calculated automatically from the Conventional Commit subjects landed since the last tag, via the [`trunk-based-release-versioning`](https://github.com/Fresa/trunk-based-release-versioning) action: a bare `feat:` bumps **minor**, a breaking change (`!` or `BREAKING CHANGE:`) bumps **major**, and everything else bumps **patch**, with major taking precedence over minor over patch when a range of commits mixes types. Developers can still rename the generated pre-release before promotion if the calculated bump isn't the one they want.

### Staging Deployments (Push to main)

Merging a pull request to `main` automatically builds the backend container image and pushes the same bytes, tagged with the commit SHA (never the calculated version — that can still change if a developer renames the pre-release before promotion), to **both** the `blog-gorman-club-stag` and `blog-gorman-club-prod` Artifact Registries - this runs on every merge regardless of whether `services/backend/**` changed, so every commit on `main`, and therefore every release tag, has an image under its SHA in both registries. It is then deployed to Cloud Run in the `blog-gorman-club-stag` project alone and the staging subdomain on Cloudflare Pages is updated; the prod push has nothing deployed against it yet, since staging is where the commit is validated first. The frontend is built the same way and on the same schedule — every merge, whether or not `services/frontend/**` changed — as a plain `dist/` (`frontend-build`), with no backend URL baked in: the bundle carries nothing environment-specific, so the identical bytes are uploaded under a `<commit-sha>/` folder into **both** the `blog-gorman-club-stag-frontend` and `blog-gorman-club-prod-frontend` buckets (`frontend-publish`). The staging site is then deployed straight from that same `dist/`, so nothing is rebuilt separately for the live staging site; the prod bucket's folder has nothing deployed against it yet, same as the prod registry.

### Pre-Release Generation

Merges to `main` calculate the next version (see Versioning above), summarize commit messages since the last tag, execute a `terraform plan -lock=false` against the production environment, and auto-generate a GitHub Pre-Release. This entry includes the plan output and the commit summary. The plan is read-only and disables state locking so it never contends with an in-flight production `terraform apply`, and so a pre-release build on `main` can never block a promotion from applying. Multiple pre-releases can accumulate on `main` without touching production.

The version number itself is calculated by its own `version` job, separate from `pre-release` and gated on nothing - unlike actually cutting the tag/release (below), computing the number is read-only, so there's no invariant it could break by running before the publish jobs finish. This is what lets `services-frontend` write the exact tag this commit is about to become into `config.json` (see Staging Deployments above and `services/frontend/README.md`), so the account panel can link to a real GitHub release instead of showing a raw commit SHA that says nothing about it. `pre-release` still recomputes the same calculation locally, but only for `last-version` and the commit log its release notes are built from - a job output is a string, not the file that calculation also writes - and takes the tag itself from the `version` job's output rather than its own recompute, so the tag staging already displays and the tag actually cut can never disagree.

`pre-release` itself stays unconditional on the diff - the same "runs every merge" invariant Staging Deployments (above) describes for `services-backend`/`services-frontend` - but it does wait on those two jobs having published and on `version` having computed the number, via a bare `needs: [services-backend, services-frontend, version]` with no `if:` of its own. Without that, a tag could be cut for a commit those publish jobs never built, breaking the "every release tag has a commit-SHA image/folder in both environments" invariant in the one way promotion can't recover from - there's nothing to deploy and nothing to roll back to.

Leaving the `if:` off is the point rather than an omission: GitHub's default for a `needs` job is to run only when every dependency succeeded, and to skip when one failed *or was itself skipped*, which is exactly the rule wanted here. #156 first wrote it as `if: always()` with a `success || skipped` check on each, which permitted the very case it was meant to stop - neither publish job has a benign skip path, since each skips only when `changed` or an infrastructure job failed (a legitimately *skipped* infrastructure job leaves them running, because their own `if` accepts `skipped` there), so every skip is an upstream failure and none of them should produce a tag. `version` has no skip path either - it runs unconditionally - so the same reasoning covers it without needing its own carve-out.

### Production Releases (Manual Promotion)

Promoting a specific pre-release tag via GitHub Actions converts it into a formal Release (e.g., `v1.0.0`) and runs, in order:

1. `terraform apply` on `blog-gorman-club-prod`, applying any infrastructure changes first.
2. Backend deploy: `gcloud run deploy` in `blog-gorman-club-prod`, pointed at `<region>-docker.pkg.dev/blog-gorman-club-prod/backend/backend:${{ github.sha }}` - the workflow resolves the target commit SHA directly from the release tag pointer (`github.sha`), and that tag is already sitting in prod's own registry, pushed there when this commit was built and deployed to staging (see Staging Deployments above). There is no registry copy and no retag: the commit SHA is the only tag an image ever carries - the release-tag-to-SHA mapping already lives in GitHub - so promotion is nothing more than deploying an image already in place. Images are **never rebuilt** for production; prod runs the identical bytes validated in staging because they are the identical bytes, not a copy of them.
3. Frontend deploy: the commit-SHA folder already sitting in the `blog-gorman-club-prod-frontend` bucket, pushed there when this commit was built and deployed to staging (see Staging Deployments above), is downloaded (`frontend-fetch`) and deployed to the production subdomain on Cloudflare Pages, with `config.json` written next to it from the just-promoted backend URL — the one step with no backend analogue, since a static site has no runtime environment of its own to read a URL from. There is no cross-project read and no copy: the bucket promotion reads from is prod's own, and the bundle is never rebuilt, since the backend URL is runtime configuration rather than baked into it (see `services/frontend/src/lib/config.ts`).

Because staging applies on every merge but prod only applies here, prod's Terraform state can lag `main` by however long it takes someone to promote - ordinarily harmless, since nothing reads a resource before it exists, but a merge-time job that unconditionally *writes* into every environment's store (per Artifact Stores above) has nothing to write into if the target resource is new and prod hasn't been promoted past the PR that added it. `apply-infrastructure-prod.yaml` (**Apply Prod Infrastructure (Manual)**, `workflow_dispatch` only) exists solely to close that gap: it runs step 1 above - `terraform apply` on `blog-gorman-club-prod` - on its own, with no release attached, so a newly-added per-environment resource can be backfilled into prod immediately after its PR merges, ahead of whenever the next promotion would otherwise get around to it. It requires typing `apply` into a confirmation input and shares Promote Release's concurrency group, since both mutate the same prod state. **This is not the normal path.** Prod infrastructure is meant to change through an actual promotion, where the accumulated plan was already visible in a pre-release's notes before anyone applied it; reach for this workflow only to bootstrap a specific new resource a merge is about to depend on, not as a routine way to push infra changes to prod.

### Rollback Strategy

Promoting a previous release tag re-runs the same promotion flow: `terraform apply` using that release's infrastructure configuration, then deploying Cloud Run in `blog-gorman-club-prod` straight to that release's own commit-SHA image tag - already sitting in prod's registry since the commit was built, so the deploy is harmless to repeat. The frontend's rollback is the same flow applied to its own bucket folder: that release's commit-SHA folder is re-fetched from `blog-gorman-club-prod-frontend` (already sitting there, so the fetch is harmless to repeat) and redeployed to Cloudflare Pages with that release's own `config.json` written beside it - no rebuild, for either service, ever.

### Pipeline Safety & Reusability

- **Concurrency Controls** — Every pipeline enforces an environment-scoped concurrency group to prevent overlapping commits from executing concurrent `terraform apply` steps or corrupting state locks.
- **Composite Actions** — Common pipeline steps (such as running Terraform plans/applies or building and pushing Docker images) are extracted into local GitHub Composite Actions inside `/.github/actions/` to keep root workflow files DRY and maintainable.

## Health Verification Strategy

Before building application features, setup is validated using a lightweight Debug Endpoint Contract:

- **Backend** — Exposes a `/health` or `/debug` endpoint returning system status, timestamp, environment metadata, and git commit SHA.
- **Frontend** — A dashboard fetches the backend `/debug` endpoint on page load.
- **Outcome** — Green indicators on `staging.example.com` and `example.com` verify that cross-cloud DNS routing, CORS policies, environment variables, and project-isolated IAM bindings are fully operational.

## Monitoring & Alerting

`/infrastructure/env/monitoring.tf` watches each environment, so staging and prod are observed identically and a policy that turns out to be noisy is discovered in staging first.

- **Uptime check** — Polls the backend's `/health` endpoint, matching on the `"status":"ok"` body rather than the 200 alone: a status code only proves something is listening on the hostname, the body proves the backend answered. The period is the longest one offered (15 minutes) on purpose — the service scales to zero, so every probe is a request that may cold-start an instance, and a minute-by-minute check would keep one warm around the clock for no diagnostic gain.
- **Alert policies** — Three, all on Cloud Run's own metrics rather than log-based metrics, so nothing has to be kept in step with the handlers: the uptime check failing from more than one region (a single failing checker is more likely to be that checker), more than N `5xx` responses in a five-minute window (counted rather than rated, since at this traffic a rate reads as noise), and 95th-percentile latency above a threshold set well clear of a cold start.
- **Notification channels** — One email channel per address in `alert_notification_emails`, kept separate rather than combined so a later policy can notify a subset without duplicating a channel. This list grants nothing; it is where a message goes, not an account admitted.
