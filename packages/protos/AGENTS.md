# packages/protos

The contract layer shared by `services/backend` and `services/frontend`. Loaded when working under `packages/protos`; the root `AGENTS.md` holds the repo-wide rules.

## Contract Layer

`/packages/protos` holds the `.proto` definitions shared across languages, built with [buf](https://buf.build) rather than plain `protoc`. It exists to close a gap plain Go/TypeScript duplication leaves open: an entity shape declared once in Go (`services/backend/internal/entity`) and hand-copied into TypeScript has nothing enforcing the two agree — a field renamed on one side is caught at runtime, if at all. A shared `.proto` message is instead the one definition both sides generate from.

**Codegen is committed, and CI fails on drift.** Committing costs one CI check (`protos-drift`, `packages/protos:drift` in moon terms: `buf generate` re-run against the tree, then `git status --porcelain` over `packages/protos`, `services/backend/internal/gen` and `services/frontend/src/gen`) and keeps every editor and Go tool working normally with no extra step - `go mod tidy` and gopls both need the generated packages to already exist on disk, not be produced on demand by a build. `services/backend/internal/gen` and `services/frontend/src/gen` are therefore committed, ordinary first-party source each language's own tooling reads like any other package - neither is modeled as build output that only exists inside a task's own sandbox. Both `services/backend/moon.yml` and `services/frontend/moon.yml` also carry an explicit `project://packages/protos` `inputs` entry on their `test` task (moon's affected detection is changed-files-only, not a graph walk - see "Building with moon" in `.github/AGENTS.md`), so a `.proto`-only edit still marks both dependents affected without moon needing to model `packages/protos` as generation input for either language's build.

**Generated code follows its consumer, not the contract it came from** — the same rule the root `AGENTS.md`'s Repository Structure section states for a future `packages/go`: the `.proto` is the shared thing, while `services/backend/internal/gen` and `services/frontend/src/gen` are build output committed for the sake of gopls/`go build` and tsc/Vite respectively, so each lives inside the service that compiles it rather than in a package of its own. `option go_package` on every proto therefore points directly into `github.com/edgorman/blog.gorman.club/services/backend/internal/gen/...`, resolved by `buf`; the TypeScript side has no proto-level equivalent to `go_package` (`buf.gen.yaml`'s `out:` alone decides where ts-proto writes), but the destination is the same call: `services/frontend/src/gen`, next to the code that imports it, not a shared `packages/node`.

**Every tool version is pinned exactly** — `buf` itself (`bufbuild/buf-setup-action`, SHA-pinned to `v1.47.2` in `pull-request.yaml`, matching the binary used locally), the `protoc-gen-go` plugin (`packages/protos/buf.gen.yaml` invokes `go run google.golang.org/protobuf/cmd/protoc-gen-go@v1.36.12`, the exact version `services/backend/go.mod` requires), and `ts-proto` (a `services/frontend/package.json` devDependency pinned without a `^`, the only npm project in the repo — `packages/protos` has no `package.json` of its own, so `buf.gen.yaml`'s local plugin entry reaches into `services/frontend/node_modules/.bin/protoc-gen-ts_proto` rather than a sibling one). `@bufbuild/protobuf`, the runtime ts-proto's generated `encode`/`decode` import, is likewise pinned exactly as a direct `dependencies` entry rather than left as an incidental transitive dependency of the `ts-proto` devDependency, since it ships in the production bundle. An unpinned version anywhere in this chain would make the drift check fail on PRs that never touched a `.proto`, which is exactly the kind of noise that gets a check disabled rather than fixed.

`ts-proto`'s `opt` flags each earn their keep rather than defaulting: `esModuleInterop=true` matches `tsconfig.app.json`'s `verbatimModuleSyntax`, which rejects ts-proto's default `import * as` star import; `useOptionals=messages` makes only *message-typed* fields optional (`field?: Submessage`), leaving scalars and repeated fields required (`id: string`, `emoji: string[]`) — see the note below on what that does and does not guarantee; `forceLong=string` decodes 64-bit integer fields to `string` rather than pulling in the `long` npm package for a `Long` class this repo has no other use for; `useDate=string` decodes `google.protobuf.Timestamp` to the RFC3339 string the wire actually carries rather than ts-proto's default `Date`, so a generated type matches the response body rather than needing conversion at the fetch boundary; `outputServices=false` is a no-op today (there is no `service` in any `.proto` here, only messages) but states plainly that a gRPC client is not what this layer is for — the backend is reached over plain REST. `strategy: all` on the ts-proto plugin entry is required by ts-proto under buf; it fails in confusing ways under buf's default per-directory invocation.

`packages/protos/moon.yml` carries three tasks: `lint` (`buf lint`) and `format` (`buf format -d --exit-code`), both scoped to `@group(sources)` (every `.proto`, `buf.yaml` and `buf.gen.yaml`); and `drift`, described above, whose `inputs` additionally cover `@group(generated)` - the two `gen/` folders themselves, workspace-relative rather than project-relative (a leading `/`), so a hand-edit to generated output marks drift affected too, not only a `.proto` edit. `drift` also depends on `services/frontend:install` (`npm ci`), since `buf.gen.yaml`'s ts-proto plugin entry resolves to `services/frontend/node_modules/.bin/protoc-gen-ts_proto`; the Go plugin needs no such dependency, since `go run google.golang.org/protobuf/cmd/protoc-gen-go@...` resolves its own module directly.

`blog.v1.AllowedEmojis` was the first message here and remains the smallest: it mirrors `entity.AllowedEmojis` and is used only as a *type* (`AllowedEmojis['emoji']` in `ReactionBar.tsx`), sharing a shape rather than values — both sides still write the five emoji out as literals. It proved the generate-and-verify pipeline; it is not what the layer is for. #168 is migrating every message that actually crosses the wire; #171 (below) is the sub-issue that revisited whether the values themselves should move in here too, and kept them out.

**Protos model the wire, not the domain and not the datastore.** Three representations already exist and this adds none: `internal/entity` carries validation and policy (`SetTitle`, `Permission`, `Subscribed`) and stays hand-written; `internal/repository/firestore` has its own `...Document` structs with converters; `internal/service` is the wire, and that is what `packages/protos` defines. The distinction is not theoretical — `blogv1.User` has no `subscribedUntil` at all because a public lookup must never disclose one, while `blogv1.CurrentUser` does, since an account may see its own. One entity, two wire messages. Generated structs cannot replace entities in any case: they carry `protoimpl` state Firestore would try to persist, and none of the entity methods.

**Responses are marshalled with `protojson`, not `encoding/json`** (`internal/service/respond.go`), because `encoding/json` on a generated struct walks its Go fields — protoimpl state included — and ignores the `protobuf` tags that decide names, presence and well-known-type encoding. Four settings there are the whole compatibility story between the two, and were chosen against captured response bodies rather than by reasoning:

- **`EmitDefaultValues`**, not `EmitUnpopulated`. Bare `protojson` drops zero-valued scalars, which would turn `"assistantEnabled": false` into an absent field and a client's `undefined`. `EmitUnpopulated` overcorrects the other way and emits `null` for unset *message* fields, which would start sending `"subscribedUntil": null` where the field is absent today. `EmitDefaultValues` is the one that matches `encoding/json`'s behaviour.
- **`UseProtoNames` off** (the default), so the wire stays lowerCamelCase — `createdAt`, not `created_at` — matching the hand-written `json` tags it replaced.
- **`DiscardUnknown` on for requests.** `protojson` rejects an unrecognized field by default where `encoding/json` ignores one; without this an older or newer client sending a field this version does not know would get a `400` where it used to be accepted. It is also what makes an additive proto change safe to deploy ahead of the client that sends it.
- **Output is compacted before it is written.** `protojson` deliberately varies its whitespace between builds, so the same message marshals to `{"id":"x","bio":""}` in one binary and `{"id":"x", "bio":""}` in the next. Two identical requests answering with byte-different bodies is a poor property for an HTTP API — it would quietly defeat any response caching or ETag added later — so `writeProto` normalizes it.

**Timestamps are `google.protobuf.Timestamp` with ts-proto's `useDate=string`**, so Go keeps `timestamppb` and TypeScript sees the RFC3339 string the wire actually carries rather than a `Date` the response body never held. The cost is that a message field has presence, so the generated type is `createdAt?: string` where a hand-written interface said `createdAt: string`. That is the wire telling the truth rather than a regression — `protojson` may omit a message field — and call sites guard it.

**`useOptionals=messages` leaves scalars required**, which is what proto3 semantics and `EmitDefaultValues` together guarantee: a scalar is always on the wire, a message may be absent. Both this file and `buf.gen.yaml` previously described the flag as making *every* field optional — it does not, and #169 corrected both. The practical consequence is the `createdAt?: string` above: optionality tracks whether a field is message-typed, not whether the server always sets it.

**`Visibility` is a plain `string` field, not a proto `enum` (#170).** `blogv1.Blog.visibility` and `blogv1.BlogRequest.visibility` carry the same `"public"`/`"private"` values `entity.Visibility` always has, unconverted. A proto3 `enum` was the other option on the table: it would give the field a closed set of valid values at the type level, on both sides, in place of a plain string either side could still send garbage into. Three things ruled it out together, not any one alone. First, wire compatibility: `protojson` serializes an enum by its member *name*, so the wire value would become `VISIBILITY_PUBLIC`/`VISIBILITY_PRIVATE` — a breaking rename of a value every stored client expectation and frontend comparison (`post.visibility === 'private'`) already depends on, for a field with no bug to fix. Second, proto3 requires an enum's first value to be its zero value, conventionally an `_UNSPECIFIED` member — but a `Visibility` has no unspecified state to model: `entity.Visibility.Valid()` accepts exactly `"public"` or `"private"` and nothing else, so an enum would need a third member that does not correspond to any value `SetVisibility` ever actually accepts, splitting the two representations of validity rather than unifying them. Third, the type safety an enum buys server-side already exists: `entity.Visibility` is a distinct Go type with its own `Valid()`, and every wire value passes through `SetVisibility` before it is ever stored (see `applyBlogRequest` and Access Control in `services/backend/AGENTS.md`) — an enum on the wire would duplicate a check that already runs, at the cost of a breaking rename. The frontend gets its own version of the same guarantee by construction rather than from the generated type: `api.ts` declares `export type Visibility = 'public' | 'private'` by hand, since the wire field itself is typed as a plain `string` and carries no such constraint of its own; `EditPost.tsx` casts the one value that arrives already validated by the server (`post.visibility as Visibility`) rather than re-deriving the union from `Blog['visibility']`, since that derivation would silently widen to `string` the moment the wire type does. Weaker at the type level is the accepted cost, and it is deliberately not the same cost `entity.Visibility.Valid()` and `SetVisibility` still pay in full on every write.

**`Comment`, `ReactionCount`, `TargetReactions`, and `PageReactions` (#171)** are the reader-engagement half of #168, and the two proto files behind them read as opposites of each other. `comment.proto`'s `Comment` follows `Blog`'s and `User`'s shape exactly: `author_username` is resolved server-side and has no counterpart on `entity.Comment`, the same reason `Blog.author_username` and `User`'s absent `subscribedUntil` are shaped the way they are (see "Protos model the wire" above); `entity.Comment`'s own moderation rules (who may delete it) stay hand-written policy. `reaction.proto` is the opposite case, and the more interesting one: `ReactionCount` and `PageReactions` have no entity to mirror at all, because what crosses the wire is an aggregate folded fresh from every reader's stored `entity.Reaction` rows (`countReactions`), not a stored row itself - the wire shape and the datastore shape were never the same thing to begin with, so there was no entity migration to even consider. `TargetReactions` (a `repeated ReactionCount` wrapper) exists purely as plumbing this pair needs and the issue didn't name: protojson can only marshal a message, never a bare top-level array, and a map value must be a message too, so both `PutReaction`/`DeleteReaction`'s response and each entry of `PageReactions.comments` need a one-field wrapper around the list `reactionCount[]` used to be. `PutReaction`/`DeleteReaction` read no request message at all - reactions are addressed (`PUT`/`DELETE .../reactions/{emoji}`) rather than toggled, so the target and the emoji are already both in the URL and the reader is the credential, leaving no body to decode.

**The `AllowedEmojis` values question (#171) is answered: leave them as literals, on both sides, permanently rather than provisionally.** The issue that added `blog.v1.AllowedEmojis` (#168's sub-issue) left this open - move the five glyphs themselves into the proto so both sides read one source, or keep sharing only the shape. Moving them in was ruled out, for two independent reasons rather than one. First, mechanically: proto3 has no field-level or file-level default for a scalar list that both `protoc-gen-go` and ts-proto would read back as the same constant without a custom protobuf option plus runtime reflection on both sides to retrieve it - a mechanism to build and maintain, not the small change the issue was sized as. Second, and more basically: the five glyphs are policy - exactly what `entity.ValidEmoji` decides, and this layer models the wire, not policy, which is the same line that keeps `entity.ValidEmoji` itself hand-written per #110's carve-out ("Protos model the wire" above). Putting the values in the proto would mean policy data living in the one place this repo has deliberately kept wire shape only. So `entity/emoji.go` and `ReactionBar.tsx` each keep their own literal `[]string`/`string[]`, typed against `AllowedEmojis['emoji']` / `genblogv1.AllowedEmojis.Emoji` rather than generated from it - a rename or resize of the field still breaks both builds, but the two lists' *values* can still drift, which is the accepted and now-documented trade rather than a gap to close later.

**`ChatMessage`, `ChatEdit`, `ChatRequest`, and `ChatReply` (#172)** are the last group in #168, and the only one where the backend is a middle layer rather than an endpoint: it calls Gemini on one side and the browser on the other. `chat.proto` models the browser↔backend hop alone, and says so directly in a file-level comment - `internal/repository/gemini`'s own hand-written wire types (`protocol.go`) stay exactly as they are, since they describe a third-party API's contract this repo does not define and cannot version; putting them in `packages/protos` would claim ownership of a shape that is Google's to change, not this service's. `ChatMessage.role` is a plain `string`, not a proto `enum`, for the same three reasons `Blog.visibility` is (see #170 above) - `entity.ChatRole.Valid()` already does the validating a closed wire type would duplicate. `ChatRequest.title`/`content` are `optional string` rather than plain `string` for the same reason `ListBlogsParams`'s optional fields are (see "Protos model the wire" above): the editor is a form with unsaved changes in it, so omitting a field ("use the saved post") and sending an explicit `""` (an author who cleared it) are different requests, and only a message field's presence - not a scalar's default - survives that distinction on the wire. `ChatHistory` (what `GetChat` answers with) exists for the same top-level-message reason `CommentThread` and `TargetReactions` do. Nothing about entitlement or rate limiting moved here: `entity.AssistantEntitlement`, the per-account rate limiter, and `SubscribedUntil` (which never crosses the wire at all, per #169) all stay exactly where they were - a proto models what a client and server exchange, not who is allowed to ask.

**#173 swept `api.ts` and `internal/service` for what #169–#172 left behind, and closed the gap that let it accumulate in the first place.** The sweep found exactly one real survivor: `internal/service/respond.go`'s `apiError`, the `{"error": "..."}` envelope every non-2xx response used, hand-declared on the backend and mirrored by an inline `{ error?: string }` type in `api.ts`'s `request()`. It is now `blogv1.ErrorResponse` (`error.proto`), the one message shared across every resource rather than owned by one - every handler fails the same way regardless of what it was doing, so there was only ever going to be one envelope, never a per-resource set to migrate piecemeal. Two smaller things came out in the same pass: `blogResponse`'s `AuthorUsername` field carried a `json:"authorUsername"` tag that had done nothing since `blogMessage` started building the wire shape by reading the field directly rather than by marshaling the struct - dead weight, removed rather than documented, since there was no wire it was ever protecting. `entity.ValidationError` (a rejected write's `{field, message}` pair) turned out to need no migration at all: `writeValidationError` already collapses it to a single string before it reaches `writeError`, so the wire has only ever carried the one envelope shape, not two.

**What deliberately stays hand-written, and why, now that the sweep is done:** `entity/access.go`'s policy table (who may do what) is authorization, not a shape exchanged over the wire - a proto models a request or response, not a decision function. `internal/repository/gemini`'s wire types (`protocol.go`) describe a third-party API's contract this repo does not define and cannot version - see #172's note on that boundary above. Every `entity.*.Validate()`/`Set*` method (and `entity.ValidationError` itself) is business logic that runs on both a freshly-decoded proto message and an internally-constructed one alike; a proto could not express "title must be non-empty" any more than a Go struct tag could, so this was never something to migrate. `debug.go`'s `debugResponse` (the Debug Endpoint Contract from "Health Verification Strategy" in `docs/architecture.md`) is the one exception #173's own CI check allowlists by name: nothing in this repository declares a second copy of that shape to drift against - the frontend dashboard that section describes was never built, and the endpoint's one real consumer, the GCP uptime check ("Monitoring & Alerting" in `infrastructure/AGENTS.md`), matches the literal `"status":"ok"` substring rather than through any type this repo controls. `services/frontend/src/lib/config.ts`'s `RuntimeConfig` is a fourth kind of exception rather than an oversight: `config.json` is written by the deploy pipeline directly (see "Production Releases" in `.github/AGENTS.md`), not served by `internal/service` at all, so there is no backend handler on the other end of it for a shared proto to keep in sync with.

**Enforcement**: `pull-request.yaml`'s `lint-check` job (`.github/workflows/pull-request.yaml`) now runs a "Wire Types" step alongside `oxlint`/`go vet` that fails the PR on two greps: any `export interface` in `api.ts` (that file's whole job is declaring API types, so the rule is easy to state and hard to get wrong), and any `json:"..."` struct tag anywhere in `internal/service`'s non-test files other than `debug.go`. This rides `lint-check`, a context `.github/settings.yml` already requires, rather than opening a new required-status-check entry the way `protos-drift` itself once had to be added after the fact (#154) - a check that can merge red is not a check, and the cheapest way to guarantee that here was to not introduce a new one.

**A wire change is a two-release problem, deliberately accepted.** Production Releases deploys the backend at step 2 and the frontend at step 3, so between them a new backend serves the previous bundle. For this repository that window is short and the blast radius is one blog, so changes are not required to be additive across two releases — but the ordering is why `DiscardUnknown` is on, and why anything larger than a field rename should be checked against it before shipping.

Giving Go a second module of its own (`packages/go`, once a second Go consumer of shared code exists — see Repository Structure in the root `AGENTS.md`) is still deliberately left for follow-up work.
